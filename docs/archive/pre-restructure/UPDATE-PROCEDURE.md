# ShadowSmile — Continuity Update Procedure

## Purpose

This file explains how future AI sessions should safely update ShadowSmile continuity documentation.

Continuity docs must reflect REALITY.

Not assumptions.

---

# PRIMARY RULE

Do NOT update continuity docs unless reality has actually changed.

Never fabricate progress.

Never mark systems “complete” without verification.

---

# WHEN TO UPDATE DOCUMENTATION

Update continuity docs when:

- major architecture changes occur
- systems become verified
- major bugs are fixed
- priorities shift
- new systems are added
- security/privacy behavior changes
- technical debt changes significantly

Do NOT spam small meaningless updates.

# IMPLEMENTED VS VERIFIED RULE

Critical doctrine:

Implemented ≠ Verified

A feature is only “verified” after:
- runtime testing
- edge-case inspection
- permission/security inspection
- mobile UX inspection
- stability inspection

Avoid false confidence.

---

# UPDATE SAFETY RULES

Before editing continuity docs:

1. inspect actual code
2. inspect runtime behavior
3. verify current architecture
4. confirm system behavior
5. avoid assumptions

Reality overrides memory.

---

Continuity updates should preserve momentum.

Avoid:
- giant rewrites
- doctrine chaos

- duplicated canon

Prefer:

- stable continuity
